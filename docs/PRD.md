# PRD: Poizon Bidding (포이즌 입찰 자동화 시스템)

> 버전: 1.0 (최근 업데이트: 2026-08-25, 주문 관리 API 연동)

> 작성일: 2026-06-15  
> 작성자: 안티그래비티 (문지영 대비마마 교시 반영)

---

## 1. 개요 (Overview)

포이즌(POIZON) Open Platform API를 활용하여, 리셀러가 **최적의 상품을 선택하고 외부 소싱 오퍼를 비교하여 수익성 있는 입찰을 자동화**할 수 있는 프리미엄 입찰 관리 도구.

---

## 2. 핵심 문제 (Problem Statement)

리셀러가 수익성 있는 입찰을 하려면:
1. 포이즌에서 현재 입찰 가능한 상품/가격 정보를 확인해야 함
2. 동시에 외부 소싱처에서 해당 상품의 시중 매입가(원가)를 확인해야 함
3. 이 두 가지 데이터를 비교해 **수익이 남는 상품에만 입찰**해야 함
4. **불필요한 상품(수익성 낮거나 이미 확인한 상품)을 걸러내어 관리 효율**을 높여야 함

현재는 이 과정을 수동으로 하기 때문에 비효율적이고 느림.

---

## 3. 목표 (Goal)

- 포이즌 입찰 정보와 외부 소싱 오퍼(최저가 상위 10개)를 **한 화면에서 비교**할 수 있게 함
- 리스팅 선택 → 가격 분석 → 입찰까지의 과정을 **최소한의 클릭**으로 처리
- **건너뛰기(Skip)** 기능을 통해 관심 없는 상품을 장부에서 숨김 처리하여 업무 집중도 향상
- **최고 수준의 시각적 완성도(Premium Aesthetics)** 확보 및 공간 효율적인 대국 레이아웃 구현
- **입찰 완료 이력**을 SKU(옵션) 단위로 즉각 확인하여 중복 입찰 방지
- **검토완료** 표시로 이미 확인한 품번·옵션을 구분하고, 미처리 상품만 집중 검토

---

## 4. 사용자 워크플로우 (User Flow)

```
[포이즌 API 검색]
    ↓ 품번(Article) 또는 브랜드명으로 조회
[백그라운드 검색 잡]
    ↓ 화면을 닫아도 워커가 브랜드 페이지를 넘기며 최대 500개까지 수집
    ↓ 손댄 품번(검토·메모·스킵·입찰·재고·알림·영구제외)은 건너뜀
    ↓ 결과 보기 시 노출가·원가가 채워진 상태로 바로 표시
[비딩 워크스페이스]
    ↓ 외부 소싱 오퍼 상위 10개 및 마진 자동 계산 확인
    ↓ (불필요 상품 발생 시) 'SKIP' 체크하여 목록에서 제외
[상세 분석 및 입찰]
    ↓ 옵션별 입찰 여부(시스템/수동) 및 검토완료 상태 확인
    ↓ 중복 입찰 시 확인 팝업 → 그대로 시도 / 가격 변경 재입찰 / 취소
    ↓ 개별 SKU 단위 또는 다중 선택 후 일괄 입찰(Batch Bid) 실행
[작업 상태 관리]
    ↓ 옵션(SKU) 또는 품번(SPU) 단위 검토완료 표시
    ↓ 품번 전체 검토완료 시 하위 옵션 일괄 완료 / 일부만 완료 시 품번에 부분 표시
[입찰 관리]
    ↓ 실데이터 입찰 목록(활성·판매·취소) 조회, 가격 수정·취소. 성공 이력은 `bid_history`
[주문 관리]
    ↓ 입찰 체결 후 주문 건별 처리(발송·검수·정산). 입찰 관리와 화면을 섞지 않음
```

## 5. 핵심 기능 (Core Features)

### 5.0 정보구조 (사이드바)

사이드바는 **검색 / 판매 / 시스템** 3그룹. 라벨은 한국어. 접으면 그룹명은 숨기고 아이콘만.

| 그룹 | 메뉴 | 라우트 | 상태 |
|---|---|---|---|
| 검색 | 검색 | `/dashboard` | 검색 보드 (품번·브랜드 조회·입찰) |
| 검색 | 검색 작업 | `/dashboard/jobs` | 백그라운드 잡 |
| 검색 | 제외 목록 | `/dashboard/excluded` | 영구 제외 |
| 검색 | 수집 몰 | `/dashboard/malls` | 원가 소스 |
| 판매 | 입찰 관리 | `/dashboard/listings` | 실데이터 입찰 내역·가격 수정·취소·자동 재입찰. `retrieve-bid/general-type-bidding-list` |
| 판매 | 주문 관리 | `/dashboard/orders` | 체결 주문 목록·발송. `order/generic_list` |
| 판매 | 수익 현황 | `/dashboard/revenue` | 기간 집계(체결 매출·수수료). 건별 주문 관리와 구분 |
| 시스템 | 설정 | `/dashboard/settings` | 수수료·자격증명 |

- **Item Search** (`/dashboard/items`)는 두지 않는다. 검색은 `/dashboard`가 담당.
- 입찰 관리는 활성·과거를 메뉴로 쪼개지 않는다. 한 화면에서 실데이터 `retrieve-bid/general-type-bidding-list`를 본다.
- 주문 관리는 입찰과 **별도 메뉴**. 체결된 주문 처리만 담당한다.

### 5.1 지능형 대시보드 (Smart Workspace)
- **2단 툴바**: 1행은 검색(타입·입력·조회·백그라운드), 2행은 결과 조작(뷰·표시·분류·건수·일괄 입찰). 부가 액션(너비 초기화·목록 비우기·마진·조회수·검색 제외 옵션)은 오버플로 메뉴
- **열 너비 유지(Resizable)**: 사용자가 설정한 테이블 컬럼 너비를 브라우저에 저장하여 다음 접속 시에도 유지
- **열 구성 (7열)**: 관리 / 상품 / **POIZON**(30일 거래가+중국 노출가) / 원가 오퍼 / 순수익 / **판매**(중국·현지) / 입찰. 병합 열은 서브라벨 클릭으로 각각 정렬. 표기 소스는 현행(SKU 노출가=`leakPrice`, 접힌 품번은 통계 `minPrice`)
- **행 상태 색 관통**: 입찰·재고·스킵·검토 배경/왼쪽 테두리는 행 전체에 보인다. 데이터 열 셀 배경 틴트는 쓰지 않음(헤더는 불투명 `bg-muted` + 열 상단 액센트로만 구분). 호버는 셀 배경을 덮지 않고 살짝 어둡게
- **펼친 옵션**: 점선 구분 + 들여쓰기 레일. 자식 행에 별도 배경을 깔아 상태 색을 가리지 않음
- **미세 애니메이션**: 품번 펼침 셰브론 회전, 관리 열 22px·입찰/알림·뷰 탭·칩은 누름 스케일. 목록 마운트·행 상태 색은 즉시(낙관적 UI). `prefers-reduced-motion`이면 비활성 (`motion-safe:`)
- **글래스 크롬**: 사이드바·워크스페이스 카드 테두리·툴바·드롭다운·팝오버·토스트는 `glass-panel`(반투명+blur). **테이블 헤더·행은 불투명**(`bg-card`)으로 상태 색을 유지. `prefers-reduced-transparency`면 솔리드
- **노출가 호버**: 셀 숫자는 바꾸지 않는다. SKU는 최저 입찰가(`globalMinPrice`)·기회 확대(`effectiveExposurePrice`)를 툴팁으로, 접힌 품번은 통계 `minPrice` 출처를 안내. SKU 클릭은 기존처럼 노출 보장가로 입찰가 채움
- **열 헤더 정렬**: 거래가·노출가·최저 오퍼/원가·순수익·판매량(중국·현지) 서브라벨·컬럼 클릭으로 오름/내림차순 (순수익 높은 순·낮은 순 포함)
- **효자 상품**: 추정 순수익이 **최소 수수료 × 2** 이상인 옵션. 순수익 셀에 Sparkles+바이올렛+`효자` 표기(행 왼쪽 테두리는 입찰/스킵/검토 상태용으로 유지). 툴바 `효자 n` 칩은 현재 목록 건수이며, 클릭 시 `수익 옵션` 뷰 + 순수익 높은 순
- **가격 알림**: SKU 입찰 열 Bell. 목표가는 입찰 입력값(있으면) 또는 현재 노출가. **노출가 ≤ 목표가**이면 도달. 푸시 아님. 툴바 `알림 n` 칩은 도달 건수이며, 클릭 시 `옵션` 뷰에서 도달 건만. 저장: `sku_status.watch_price`
- **권장 입찰가**: 마진 설정의 **목표 마진율**(원가 대비 순수익). 1등 오퍼 원가가 있으면 입찰 열에 `권장 ₩`이 뜨고, 클릭 시 입찰 입력을 채운다. 수수료율·최소/최대 수수료 캡을 반영해 역산 (`system_settings.target_margin_rate`)
- **실수령액**: 입찰가 − 수수료. **전부 KRW** (POIZON `currency=KRW`, 원가 오퍼도 원). 환율 변환 없음. 순수익 = 실수령 − 1등 오퍼 원가. 입찰 열 `실수령 ₩`
- **카테고리 필터링**: 검색 결과 내에서 특정 분류(신발, 의류 등)만 골라보기 지원
- **뷰 탭 (데이터 모델 분리)**: `품번`(SPU 계층) / `옵션`(전 SKU flat) / `수익 옵션`(추정 원가 대비 수익 SKU만) — 표시 필터와 독립
- **표시 필터**: 「표시」 드롭다운 1개 — `전체` / `미처리` / `스킵 숨김` / `검토 숨김`. 검색 시점 제외(스킵·검토완료)는 잡 `options`·오버플로 검색 옵션으로 유지
- **백그라운드 검색 작업**: 검색 조건만 등록하고 즉시 반환. 워커가 페이지를 넘기며 손 안 댄 품번을 최대 500개까지 모음. 진행률·부분 실패·완료 결과는 `/dashboard/jobs`에서 관리. `결과 보기`는 진행 중이어도 가능(노출가·원가 포함). 체크한 품번만 `선택 가격 갱신`. 같은 검색어의 손댄 품번은 `손댄 품번 합치기`
- **관리 열 정규화**: SKU/SPU 공통 슬롯 순서 `선택·입찰·재고·검토·메모·스킵`, SPU 전용(제외·삭제)은 케밥 메뉴
- **보드 분해**: `search-board.tsx`는 오케스트레이터. 툴바·결과 테이블·SPU/SKU 행은 컴포넌트, 검색·추천가 큐·원가 오퍼는 `hooks/use-poizon-search.ts` / `use-sku-recommendation-queue.ts` / `use-source-offers.ts`
- **접근성 (F15)**: 관리 열 22px 아이콘 단독 버튼은 `aria-label`(밀도 유지). 툴바·사이드바 아이콘 단독 버튼은 md 이상에서 텍스트 라벨. 수익/손실은 `▲ +₩` / `▼ -₩`. 목록 비우기·행 삭제는 확인 단계

### 5.2 건너뛰기 및 제외 관리 (Skip & Exclude)
- **Skip 체크**: 특정 SKU(옵션)나 SPU(상품)를 건너뛰기 목록에 추가하여 시각적으로 투명하게 처리. 활성 표기는 **EyeOff + 슬레이트(회색)** — 부분 검토(골드)와 색·아이콘을 분리
- **영구 제외(Exclude)**: 수익성이 극히 낮거나 한국 시장에 맞지 않는 품번은 DB에 영구 등록하여 향후 검색 결과에서 원천 차단
- **저장소 동기화**: Skip 상태는 Supabase DB에 저장되어 기기가 바뀌어도 유지됨

### 5.3 입찰 이력 추적 (Bid History Tracker)
- **SKU 단위 입찰 표시**: 세부 옵션(사이즈) 행마다 입찰 여부를 Gavel 아이콘으로 표시
- **시스템 입찰 (파란색)**: 내 사이트 API로 입찰한 경우 — `bid_history` + DB 기록
- **수동 표기 (빨간색)**: 실데이터(포이즌 판매자 센터)에서 이미 입찰한 옵션 등, 사용자가 `+` 버튼으로 직접 표기 — `sku_status.manual_bid_marked`
- **수동 표기 해제**: 빨간 Gavel 또는 「수동표기」 배지 클릭으로 해제 (호버 시 X 오버레이, 툴팁 안내)
- **SPU 요약**: 품번 **상품명 영역**에 `입찰 n/m` 인라인 배지 + 호버 툴팁 (관리 열 체크박스 아래 Gavel 없음)
- **행 시각 구분**: 입찰된 옵션 행은 **선명 유지 + 파랑/빨강 배경 음영**(행 전체). 스킵=슬레이트 테두리+흐림, 검토완료=에메랄드 테두리+흐림, 재고=에메랄드 선명
- **활동 히스토리**: SKU/SPU 행에 `최종 · 날짜 · 활동` 1줄 (입찰·수동표기·검토·스킵·메모 중 최신)
- **중복 입찰 방지**: 실데이터에 동일 SKU 입찰 존재 시(에러 `91800500`) 확인 팝업 — 기존 입찰 정보 표시 후 그대로 시도 / 가격 변경 재입찰 / 취소

### 5.4 검토완료 (Review Complete)
- **옵션(SKU) 단위**: 각 세부 옵션 행에 검토완료 체크 — 해당 사이즈만 검토 끝 표시
- **품번(SPU) 단위**: 대표 품번 행 체크 시 **모든 하위 옵션 일괄** 검토완료 / 해제
- **부분 완료 표시**: 일부 옵션만 검토완료면 품번 체크 = **CircleDot(점 원) + 골드(amber)**, 배지 `검토 n/m`. 스킵(EyeOff·슬레이트)과 색·아이콘을 분리
- **전체 완료 표시**: 모든 옵션(또는 품번 일괄) 완료 시 **에메랄드 왼쪽 테두리 + 녹색**, 행 흐림 처리
- **입찰 성공 연동**: 입찰 성공 시 **해당 SKU만** 검토완료 처리 — 품번(SPU) 전체는 자동 완료하지 않음
- **즉시 반영**: 검토완료는 낙관적 UI — 로딩 스피너 없이 클릭 즉시 반영, DB 저장은 백그라운드
- **새로고침 복원**: 검색 결과 로드 시 SPU 기준으로 `sku_status`·`item_status` 재조회 (실패 시 피드백 표시)
- **미처리 필터 연동**: 품번 검토완료 또는 **모든 옵션** 검토완료된 품번만 "미처리 상품만 보기"에서 숨김 (입찰만 있는 품번은 유지)

> **입찰 표시 vs 검토완료**: 망치(Gavel) = "이 옵션 입찰함", 체크 = "이 옵션/품번 검토 끝" (입찰과 무관하게 사용 가능)

### 5.5 수익성 분석 및 입찰 실행
- **외부 소싱 오퍼 비교**: 품번 검색 시 여러 몰의 오퍼를 집계해 **가격이 낮은 순 상위 10개**를 제시
- **기본 원가 규칙**: 마진 계산의 기본 원가는 상위 10개 오퍼 중 **1등 오퍼 가격**을 사용
- **동일 몰 중복 허용**: 같은 몰이라도 다른 상품 페이지/프로모션/옵션이면 상위 10개에 중복 포함 가능
- **다이나믹 마진 계산**: DB에 설정된 수수료 정책(최소 15,000원, 최대 45,000원 등)을 기반으로 실시간 순수익 산출. 입찰·노출가·수수료·원가는 모두 KRW. 환율 변환은 하지 않음
  - 실수령 = 입찰가 − 수수료 (요율 + min/max 캡)
  - 순수익 = 실수령 − 1등 오퍼 원가
  - 권장 입찰가 = 실수령이 `원가 × (1 + 목표 마진율)` 이상이 되는 최소 입찰가
- **일괄 입찰(Batch Bid)**: 복수의 SKU를 선택하여 한 번의 클릭으로 대량 입찰 처리

### 5.6 검색 작업 관리
- **잡 등록 즉시 반환**: 검색창의 `백그라운드` 버튼은 검색 조건만 저장하고 즉시 반환. **워커가 없으면 대기에 멈춘다**
- **연속 수집 (최대 500)**: 브랜드는 API 페이지(50건)를 넘기며 **손 안 댄 품번**을 최대 500개 적재할 때까지 계속한다. 품번(콤마) 검색은 한 번에 처리하되 상한은 동일. 화면의 `조회`는 단건·빠른 확인용. 잡 결과를 연 뒤 `더 불러오기`는 쓰지 않고, 더 모으려면 다시 `백그라운드`
- **손댄 품번 제외**: 연속 수집은 영구제외·스킵·검토완료·메모·입찰(시스템/수동)·재고·가격 알림이 **옵션 하나라도** 있으면 그 품번을 넣지 않는다. 같은 조건으로 다시 걸면 손댄 것은 건너뛰고 아직 안 본 것만 최대 500개 더 모은다
- **손댄 품번 합치기**: 같은 검색어의 과거 잡에서 손댄 품번만 현재 목록에 합친다. 잡을 지우면 사진·가격 스냅샷은 사라지고 검토/메모 기록만 남는다
- **상시 백엔드 워커**: `search_jobs`를 폴링해 검색·통계·원가 오퍼·SKU 노출가(추천가)를 수행. 페이지마다 DB에 저장해 중단 후에도 이어서 수집
  - **로컬**: `pnpm worker`가 **필수**. `pnpm dev`만으로는 큐를 집어가지 않음. 한 프로세스가 페이지를 이어서 처리
  - **배포**: `POST/GET /api/cron/search-worker` + 플랫폼 크론(예: Vercel Cron). `CRON_SECRET` Bearer 인증.
    호출당 대기/`running`(잠금 없음) 잡 1건을 claim하고 **1페이지** 처리. 서버리스 타임아웃에 걸리면 `locked_at` stale 회수 후 재시도
- **워커 미기동 안내**: 대기 잡이 45초 넘게 `queued`면 `/dashboard/jobs`에 안내 배너. 사이드바는 진행 중 스피너 대신 대기 배지
- **진행률 및 재실행**: `/dashboard/jobs`에서 상태, 적재 수/500, 제외 건수, 부분 실패 사유, 재실행/삭제 제공. `item_count > 0`이면 진행 중이어도 `결과 보기`
- **결과 인계**: 잡 payload에 통계·원가 오퍼·노출가가 들어 있어 화면이 추가 조회 없이 바로 표시. 시간은 지나면 `선택 가격 갱신`(체크한 품번만 노출가·원가 재조회, 잡 payload 동기화)

### 5.7 수집 몰 관리 (`/dashboard/malls`)
- **활성 스위치**: 원가 수집에 포함할 몰을 켜고 끔 (`source_malls.is_active`). 캐시 TTL(1h) 때문에 즉시 반영이 필요하면 「원가 캐시 비우기」
- **수집 상태(점검)**: 품번으로 실수집 프로브 → `ok`(오퍼 있음) / `empty`(오퍼 없음) / `failed`(실패) / 미점검
  - 건수·최저가·시각·메시지를 행에 저장·표시. 개별·전체·「오래된만」(미점검/24h+) 점검 지원
- **품질 표시**: 코드 레지스트리의 `reliability` — `정상` / `제한적`(예: G마켓 Akamai 403)
- **상태 필터**: 활성·점검 결과별로 목록을 좁혀 회귀(조용한 0건)를 바로 확인
- **초기 타깃 몰**: 롯데ON · 롯데백화점몰 · 롯데아이몰 · 무신사 · 코오롱몰 · SSG · G마켓(제한적) · **나이키 코리아** · **이랜드몰** · **ABC마트** · **29CM** · **W컨셉**
- **회귀 감시**: `pnpm check:offers`로 몰별 실수집 프로브(품번 목록). `failed`면 exit 1.
  - `--write-db` 시 `source_malls` 최근 점검 컬럼 갱신 → `/dashboard/malls`에서 바로 확인
  - 대시보드 「전체 점검」·「오래된만」과 동일 판정(`ok`/`empty`/`failed`)
- **몰 추가 절차** (UI에서 등록만으로는 불가 — 파서 코드 필수):
  1. `lib/sourcing/providers/{key}.ts`에 `SourceOfferProvider` 구현 (`key`, `label`, `fetchOffers`)
  2. `lib/sourcing/registry.ts`의 `SOURCE_MALL_DEFINITIONS`에 등록 (`homepage`, `reliability`, `notes`)
  3. 배포 후 `/dashboard/malls` 진입 시 `syncSourceMalls()`가 DB 행을 자동 보강
  4. 점검 품번으로 「연결 점검」→ `ok` 확인 후 활성 유지

### 5.8 입찰 관리 (`/dashboard/listings`)

지금까지 넣은 입찰을 **한 화면에서** 조회·수정·취소한다. 활성/과거를 메뉴로 나누지 않는다.

- **목록**: `POST /dop/api/v1/pop/api/v1/retrieve-bid/general-type-bidding-list` (문서 apiDetail/51)
  - 구 `listing/list`는 실데이터에서 404(`前方拥挤了`). 쓰지 않음
  - 페이지는 `exclusiveStartOffsetId`(첫 페이지 0) → 응답 `lastOffsetId`. **총건수는 없음** — 화면에 합계를 만들지 않고 「이 페이지 N건 · 다음으로 이어 조회」만 표기
  - 상태(`tradeStatus`)는 요청에 넣는다. 생략하면 매진 위주로 돌아온다
- **상태 탭**: 활성 `2` · 거래중 `0` · 매진 `3` · 취소 `1`
- **노출 필터** (현재 페이지, `exposureItemList`): 중국/한국 구매자 미노출
- **최저가 필터** (현재 페이지, `recommend-bid/price`): 중국 최저가 미달(`price > globalMinPrice`) · 한국 최저가 미달(`price > leakInfos[KR].leakPrice`)
- **보강**: 현재 페이지를 `sku-basic-info/by-spu`로 품번·이미지를, `recommend-bid/price`로 최저가를 붙인다. `by-sku-ids`·추천 배치는 실데이터 404
- **액션**: 행 가격 수정·선택 가격 조정(`update-bid/normal-autonomous-bidding`), 취소(`cancel-bid/cancel-bidding`), CSV 내보내기
- **폴백**: API 실패 시 로컬 `bid_history` (「로컬 이력」)
- **자동 재입찰**: 활성 입찰에 `follow-bidding/submit`으로 최저가 추종을 건다. 목록은 `auto-follow-bidding/list`. 가격 조정은 플랫폼이 수행하며, 내 사이트는 등록·조회·해제만 한다
- 검색 보드의 SKU Gavel(시스템/수동 표기)과 역할이 다르다. 보드는 행 단위 표시, 이 화면은 **내 입찰 장부**

### 5.9 주문 관리 (`/dashboard/orders`)

입찰이 **체결되어 주문이 생긴 뒤**의 건별 처리. 입찰 관리와 화면을 섞지 않는다.

- **목록**: `POST /dop/api/v1/pop/api/v1/order/generic_list` (`skuId`/`spuId`는 global ID)
  - 생성일 `start_created`~`end_created` **호출당 최대 7일**. 화면 기본은 최근 7일
  - **7일을 넘기면** 7일 윈도로 분할 조회한 뒤 주문번호로 합친다. 선택 가능한 상한은 **90일**
  - `order_type`: `NORMAL_SALE`(현물) / `CONSIGN`(위탁) / `PRE_SALE`(프리세일) / `DIRECT`
  - 페이지: 7일 이하는 `page_no`/`page_size`. 분할 조회는 합친 목록을 화면에서 자른다
- **상태 탭** (API `order_status`):
  - 발송 대기 `2000` · 판매자 발송 `2100` · 플랫폼 입고 `2200` · 검수 완료 `2500`
  - 플랫폼 발송 `2600` · 배송 중 `2650`~`3040` · 거래 성공 `4000`
  - 실패/마감 `7000`/`8000`/`8010` · 환불·반품 `8080`
  - 미결제 `1000`은 「대기」로 묶음
- **발송**: `POST /dop/api/v1/pop/api/v1/order/delivery` — 발송 대기(`2000`)만. 운송사 + 송장번호
  - 운송사 목록 API는 실데이터 404. 문서 ID(UPS 7 등) + 직접 입력
- **QC**: 목록 `identifyType`·`onlineIdentifyStatus`. `Query Order QC Result` 후보는 실데이터 404
- **비범위**: 위탁 입고(Consignment inbound) 전용 API. 기간 집계는 §5.11

### 5.10 자동 재입찰 (입찰 관리 안)

지정한 **최저가(`lowestPrice`)** 와 **추종 방식(`followType`)** 으로 플랫폼이 경쟁가에 맞춰 가격을 움직인다.

- **등록**: `POST /dop/api/v1/pop/api/v1/auto-follow-bidding/submit` — `biddingNo`/`sellerBiddingNo`, `lowestPrice`, `followType`(3·4·5·6), `autoSwitch`, `countryCode`, `currency`. 구 `follow-bidding/submit`은 실데이터 404
- **목록**: `POST /dop/api/v1/pop/api/v1/auto-follow-bidding/list` (계정에 따라 500이 날 수 있음)
- **해제**: cancel 계열은 실데이터 404. 등록만 제공
- 입찰 관리 활성 행에서 연다. 워커가 가격을 돌리지 않는다

### 5.11 수익 현황 (`/dashboard/revenue`)

주문 **건별 처리(§5.9)와 구분**한 기간 집계.

- 같은 `order/generic_list`를 7일 윈도로 나눠 모은다. 기본 최근 30일, 상한 90일
- **체결 매출** = `pay_amount`(없으면 `amount`). **플랫폼 수수료** = `poundage_detail` 합(없으면 설정 요율로 추정)
- **추정 실수령** = 매출 − 수수료. **원가는 주문에 없음** — 검색 보드 순수익과 숫자를 맞추지 않는다
- 일별 매출·상태별 건수. 거래 성공만 따로 합산

- 네이버 개발자센터의 **검색 > 쇼핑 API**는 2026-07-31 종료되어 더 이상 신규 신청·기존 키 호출이 불가

- 초기 구현은 2~3개 핵심 몰부터 시작해 end-to-end를 안정화한 뒤 확장
- 쿠폰·네이버페이 경유 할인까지 100% 재현하는 것은 범위 밖이며, 초기 목표는 **직접 구매 가능한 오퍼 상한 가격** 확보

## 9. 데이터 소스 정의 및 검증 메모 (2026-06-16)

> 판매자센터(공식) 데이터와 서버 표기 값의 정합성을 맞추기 위한 기준 정리.

### 9.1 판매량 (30일) — 정의·구현·한계 (2026-06-18 갱신)

#### 지표 정의 (판매자센터 기준)

- **중국 시장 30일 판매량** = 판매자센터 "중국 시장" 컬럼 값 (export의 `총 판매량`과 동일 지표, 라벨만 다름)
- **현지(한국) 30일 판매량** = 판매자센터 "현지 판매자" 컬럼 값
- **품번(SPU) 30일 판매량** = 세부 옵션(SKU)별 30일 판매량의 **합산값**

#### 내 사이트 구현 (현재 적용)

| 항목 | 내용 |
|------|------|
| API 엔드포인트 | `globalSpuId` 확보 후 **`sku-basic-info/by-global-spu` 우선**, 실패 시 **`by-spu` 폴백** (`getSpuStatistics`) |
| region 조회 | **`KR` + `CN` 이중 호출**. CN 성공 시 CN 통계 우선, 실패 시 KR 폴백 |
| 필드 | `commoditySales.globalSoldNum30`(중국), `localSoldNum30`(현지) |
| SKU 목록 | `skuList` + `skuStats`를 `skuId` 기준 **union 머지** → 옵션 누락 방지 |
| 표기 규칙 | `0` = 무판매, `—` = 미수신, `1~4` = `<5`, `≥100` = 백 단위 내림 + `+` (예: 490→`400+`) |

#### UI 컬럼 ↔ API 필드 매핑

| 내 사이트 UI 컬럼 | API 필드 | SKU 행 (펼침) | SPU 행 (접힌 품번) |
|------------------|----------|---------------|---------------------|
| **30일 판매량 (중국)** | `commoditySales.globalSoldNum30` | `getSkuSalesValue(sku, skuStatsCN, "globalSoldNum30")` | 하위 SKU `globalSoldNum30` 합산 → `item.salesVolume` |
| **30일 판매량 (현지 판매자)** | `commoditySales.localSoldNum30` | `getSkuSalesValue(sku, skuStatsCN, "localSoldNum30")` | 하위 SKU `localSoldNum30` 합산 → `item.localSalesVolume` |

**값 조회 우선순위** (`lib/utils/sales-volume.ts` → `getSkuSalesValue`):

1. `region=CN` 통계(`skuStatsCN`)에서 동일 `skuId`의 해당 필드
2. 없으면 `region=KR` 통계(`skuStats`, `resolveSkuDetails` 머지 결과)의 해당 필드
3. `commoditySales === null`이면 API 기준 **0**
4. 둘 다 없으면 **미수신** → 화면 `—`

표시 전 `formatSalesVolume()`으로 `0` / `—` / `<5` / `100+` 포맷 적용.

관련 코드: `app/actions/poizon.ts`, `hooks/use-poizon-search.ts`, `hooks/use-sku-recommendation-queue.ts`, `components/dashboard/search-board.tsx`, `lib/utils/sales-volume.ts`

#### 검증 결과 (품번 `TLTCM26521`, SPU `40700983`)

**오픈 API(`open.poizon.com`)와 판매자센터(`seller.poizon.com`) 간 30일 판매량이 SKU마다 다를 수 있음.**

| 구분 | 예시 | 비고 |
|------|------|------|
| 일치 | 민트110=48, 민트115=22, 블랙95=`400+`, 블랙110=`1,700+` | 포맷 적용 후 센터와 일치 |
| 불일치 | 블랙100: API **25** vs 센터 **2,100+** | `by-spu`·`by-global-spu`·`by-sku` 모두 25 동일 |
| 현지 전체 | API `localSoldNum30` = **0** (전 SKU) | 센터는 14, 43, `200+` 등 실값 존재 |

**진단 결론**

- 판매자센터는 내부 게이트웨이 `intl-commodity/admin/global/sku/sku-info/by-global-spu` 사용 (로그인 세션)
- 오픈 API의 `by-global-spu`는 경로는 유사하나 **동일 수치를 반환하지 않음** (App Key만으로는 센터 parity 불가)
- `region=CN`은 오픈 API에서 `20899003 Overseas region information not found`로 차단
- `by-spu-ids`, `admin/.../by-global-spu`(오픈 도메인)는 404

→ 코드/UI 개선만으로는 센터 100% 일치가 불가능한 구간이 있으며, **POIZON 오픈플랫폼 문의**가 필요 (상세: `docs/TODO.md` §8.3)

### 9.2 "중국 노출가" (필드 매핑 확정 / 표기는 현행 유지)

입찰화면 3박스 ↔ `recommend-bid/price` `data` 필드 (실측 2026-08-24, `pnpm dump:recommend`):

| 입찰화면 박스 | API 필드 | 비고 |
|---|---|---|
| **① 중국 구매자 페이지 노출 보장** | `leakInfos[buyerRegion="CN"].leakPrice` | **내 사이트 SKU 「중국 노출가」·입찰가 자동입력. 그대로 유지.** |
| **② 중국 시장 현재 최저 입찰가** | `globalMinPrice` (`asiaMinPrice`와 표본에서 동일) | 셀 숫자는 아님. SKU 노출가 호버 툴팁 |
| **③ 판매 기회 확대** | `effectiveExposurePrice` | 셀 숫자는 아님. SKU 호버 툴팁. 일부 SKU는 필드 자체 없음 |

- 품번(SPU, 접힌 행)의 「중국 노출가」는 통계 API `minPrice/marketPrice` → SKU `leakPrice`와 숫자가 다를 수 있음. 표기는 유지하고 호버로 출처를 안내
